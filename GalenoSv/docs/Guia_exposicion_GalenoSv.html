1. Qué es GalenoSv

GalenoSv es una aplicación web para organizar información clínica y odontológica. En la fase actual permite administrar catálogos, clínicas, personas, documentos, medios de contacto, roles, procedimientos, pasos clínicos, consultas, órdenes de examen y resultados.

La aplicación no se planteó como una colección de formularios aislados. Las páginas siguen las relaciones de la base de datos: primero se preparan catálogos y definiciones; después se registran personas; finalmente se ejecuta el flujo de atención.

3. Arquitectura del proyecto

Usuario
↓ evento en XHTML / PrimeFaces
boundary.jsf · Modelo de vista
↓ invoca operaciones
control · DAO / EJB
↓ usa EntityManager y JPA
entity · Entidades
↓ mapeo relacional
PostgreSQL

entity: representación de los datos

Cada entidad representa una tabla. Sus anotaciones indican tabla, columnas, clave primaria y relaciones. Las entidades no controlan botones ni muestran mensajes; su responsabilidad es describir datos y asociaciones.

control: acceso a datos

Los DAO contienen la comunicación con JPA. DefaultDAO<T> reúne operaciones repetidas como buscar, listar, contar, crear, modificar y eliminar. Los DAO concretos indican la entidad que administran y agregan consultas particulares cuando hacen falta.

boundary.jsf: estado y comportamiento de la vista

Los modelos JSF reciben los eventos de las páginas, mantienen el registro seleccionado y deciden si el formulario está creando, modificando o en reposo. Se llaman Model porque ese es el nombre usado en el flujo actual del curso, aunque técnicamente actúan como modelos de vista o backing beans.

boundary.conversores: traducción entre representaciones

Los convertidores resuelven diferencias entre lo que maneja la interfaz o JPA y el tipo Java esperado. Son parte de la frontera de la aplicación, por eso se ubicaron debajo de boundary.

webapp: presentación

Las páginas XHTML definen tablas, formularios y acciones. No contienen consultas SQL ni crean un EntityManager; delegan ese trabajo a los modelos y DAO.

Pregunta: ¿Boundary y Control son lo mismo?
No. Boundary atiende la interacción con la interfaz. Control ejecuta la lógica de acceso a datos. Separarlos evita que la página conozca detalles de persistencia.

4. Recorrido de una operación CRUD

El mismo patrón se repite en las páginas, con variaciones según las relaciones de cada entidad.

  1. JSF construye la página y obtiene el bean mediante su nombre, por ejemplo #{tipoExamenModel}.
  2. @PostConstruct inicializa un LazyDataModel.
  3. PrimeFaces solicita una página de registros.
  4. El modelo llama a DAO.findRange(first, max) y DAO.count().
  5. Al presionar Nuevo, el modelo crea una entidad y cambia el estado a CREAR.
  6. Al guardar, el modelo valida y llama a DAO.crear(registro).
  7. El DAO usa EntityManager.persist.
  8. PrimeFaces actualiza por AJAX la tabla, el detalle y los mensajes.
p:commandButton → método del Model → método del DAO → EntityManager → PostgreSQL
PostgreSQL → resultado → Model → actualización AJAX → usuario

5. Por qué existen clases abstractas y genéricos

El proyecto tiene veinte entidades con operaciones CRUD parecidas. Repetir la misma paginación, selección, persistencia y mensajes en veinte clases aumentaría los errores. La abstracción conserva el comportamiento común y obliga a cada clase concreta a resolver lo que cambia.

DefaultDAO<T>

El parámetro T representa el tipo de entidad. Por ejemplo:

public class TipoExamenDAO extends DefaultDAO<TipoExamen> {
    public TipoExamenDAO() {
        super(TipoExamen.class);
    }
}

Así, los métodos heredados reciben y devuelven TipoExamen. Esto aporta seguridad de tipos: no se puede enviar accidentalmente una Persona a un DAO de exámenes.

AbstractModel<T>

Centraliza la tabla diferida, selección, botones y mensajes. Cada modelo concreto proporciona:

  • El DAO correspondiente.
  • La forma de construir un registro nuevo.
  • La forma de obtener y convertir su identificador.
  • Las reglas especiales de su pantalla.
Pregunta: ¿No está demasiado factorizado?
La abstracción se limita al CRUD que realmente se repite. Las relaciones, búsquedas y validaciones especiales permanecen en modelos concretos. No se intentó construir un generador universal de pantallas; se reutilizó únicamente el comportamiento común comprobable.
Pregunta: ¿Por qué se eliminaron algunos @Override?
Cuando una clase concreta repetía exactamente el comportamiento heredado, la sobrescritura no aportaba nada. Se conservaron los @Override donde la entidad necesita crear su UUID, sincronizar relaciones, personalizar una búsqueda o cambiar el comportamiento del CRUD.

6. Modelo de datos y flujo funcional

El flujo correcto no depende únicamente del orden visual del menú. Depende de qué registros necesita cada relación.

Fase A: configuración

  1. Clínica: establecimiento donde trabajan o son atendidas las personas.
  2. Rol: paciente, odontólogo, asistente u otro.
  3. Tipos: tipos de documento, medios de contacto y exámenes.
  4. Examen: examen específico, como radiografía panorámica.
  5. Procedimiento: tratamiento, como limpieza o extracción.
  6. Pasos: actividades que forman un procedimiento, su secuencia y los exámenes requeridos.

Fase B: registro de personas

  1. Persona: datos personales.
  2. PersonaRol: vincula persona, clínica y rol.
  3. Documento: vincula persona y tipo de documento.
  4. MedioContacto: vincula persona y tipo de contacto.

Fase C: atención clínica

  1. Consulta: se abre para una PersonaRol.
  2. ConsultaProcedimiento: registra el procedimiento aplicado dentro de la consulta.
  3. ConsultaProcedimientoPaso: registra la ejecución de un paso y la persona responsable.
  4. OrdenExamen: nace desde el paso de procedimiento ejecutado.
  5. ExamenResultado: almacena resultado, interpretación y ruta del atestado.
Ejemplo narrado:
Se registra a Juan Pérez como persona y se le asigna el rol Paciente en una clínica. Se abre una consulta por dolor en un molar, se agrega el procedimiento de evaluación, se registra el paso radiológico, se crea una orden y finalmente se guarda el resultado de la radiografía panorámica.

7. Caso clave: Examen y TipoExamen

Primero se distingue el significado

ConceptoEjemploEntidad
Categoría o clasificaciónRadiológicoTipoExamen
Examen específicoRadiografía panorámicaExamen
Asociación entre ambosRadiografía panorámica pertenece a RadiológicoExamenTipoExamen
Examen ← ExamenTipoExamen → TipoExamen

ExamenTipoExamen no es un formulario inventado para la interfaz. Es una entidad real que representa la tabla intermedia y además tiene datos propios: identificador, fecha de creación y observaciones. Por eso se modela explícitamente, en lugar de ocultarla como una relación simple.

Justificación del genérico del modelo

public class ExamenTipoExamenModel
        extends AbstractModel<ExamenTipoExamen>
        implements Serializable {
}

Esta declaración es correcta en GalenoSv porque la responsabilidad principal del modelo es crear, listar, modificar y eliminar registros de la relación ExamenTipoExamen. Los demás tipos de la clase confirman esa decisión:

ExamenTipoExamenDAO dao;
DefaultDAO<ExamenTipoExamen> getDao();
LazyDataModel<ExamenTipoExamen> modelo;
ExamenTipoExamen nuevoRegistro();

La búsqueda del elemento que se asociará sí trabaja con TipoExamen:

TipoExamenDAO tipoExamenDAO;
TipoExamen tipoExamenSeleccionado;
Cómo explicarlo al ingeniero:
El ejemplo de clase podía usar AbstractModel<TipoExamen> si su única responsabilidad era buscar o seleccionar tipos. Al integrarlo con nuestra base, el modelo pasó a administrar la entidad de enlace completa. Conservamos la búsqueda con TipoExamen, pero el CRUD pertenece a ExamenTipoExamen.

¿Qué pasaría si se cambiara a AbstractModel<TipoExamen>?

No sería un simple cambio de nombre. El contrato heredado exigiría que getDao(), nuevoRegistro(), selectionHandler() y la tabla trabajaran con TipoExamen. El DAO actual trabaja con ExamenTipoExamen; por lo tanto, los tipos serían incompatibles o se perdería el CRUD de la relación.

Respuesta corta para la exposición:
El tipo genérico expresa qué entidad administra el modelo. Como este modelo persiste la relación, debe usar ExamenTipoExamen. El objeto TipoExamen se usa como opción seleccionable dentro de esa relación.

8. Por qué @Dependent en el modelo de detalle

ExamenModel es @ViewScoped: mantiene el examen seleccionado mientras el usuario permanece en la vista. Dentro de él se inyecta ExamenTipoExamenModel, que es @Dependent.

@Named("examenModel")
@ViewScoped
public class ExamenModel implements Serializable {
    @Inject
    ExamenTipoExamenModel examenTipoExamenModel;
}

@Named("examenTipoExamenModel")
@Dependent
public class ExamenTipoExamenModel { ... }

Al ser dependiente, el modelo secundario vive asociado al objeto que lo recibe. Esto permite que el detalle de tipos acompañe al examen seleccionado y evita administrar otra vista independiente para una relación que se muestra dentro de Examen.xhtml.

Pregunta: ¿Por qué hay 20 modelos y solo 19 páginas?
Porque ExamenTipoExamenModel no representa una página separada. Es el modelo del detalle incluido en la pestaña Tipos de examen dentro de Examen.xhtml.

9. Pestaña, diálogo y autocompletado

Examen.xhtml usa un p:tabView con dos contextos:

  • Datos del examen: nombre, activo y observaciones.
  • Tipos de examen: asociaciones del examen seleccionado.

La segunda pestaña se deshabilita mientras no exista un examen seleccionado. Esto evita intentar relacionar tipos con un examen que todavía no fue guardado.

Para elegir un tipo se abre un p:dialog con p:autoComplete. El autocompletado llama a TipoExamenDAO.findByNombreLike, respaldado por una NamedQuery. La búsqueda comienza con tres caracteres para evitar consultas amplias por cada tecla.

¿TabView o Wizard?

ComponenteCuándo convieneDecisión actual
p:tabViewCuando son secciones relacionadas y se puede volver libremente entre ellas.Adecuado para editar el examen y luego sus asociaciones.
p:wizardCuando existe un proceso obligatorio paso a paso con validación antes de avanzar.Sería útil si el alta completa exigiera una secuencia rígida.

No se eligió wizard porque la pantalla actual administra un maestro y su detalle, no un trámite lineal que deba completarse una sola vez.

10. Los dos convertidores no hacen lo mismo

TipoExamenConverter: convertidor de JSF

En HTML, el valor seleccionado llega como texto. El autocompletado necesita recuperar un objeto TipoExamen. El convertidor transforma UUID en entidad y entidad en UUID:

navegador envía String UUID
↓ getAsObject
TipoExamenDAO.find(UUID)
↓
objeto TipoExamen

UUIDConverter: convertidor de JPA

Implementa AttributeConverter<UUID, UUID> para declarar explícitamente la conversión de identificadores UUID al tipo UUID de PostgreSQL. No participa en componentes JSF ni busca entidades.

Pregunta: ¿Por qué están en boundary.conversores?
Se agruparon siguiendo la organización del proyecto base. NetBeans puede mostrar boundary, boundary.jsf y boundary.conversores como paquetes separados si usa vista plana; físicamente los dos últimos están debajo de la carpeta boundary.

11. Persistencia y decisiones de las entidades

UUID como identificador

Los registros generan UUID en Java antes de persistirse. Esto evita depender de una secuencia numérica central y coincide con las columnas UUID de PostgreSQL.

OffsetDateTime para fecha y hora

Los campos temporales usan OffsetDateTime. Se eliminó el patrón antiguo Date más @Temporal, porque la API moderna de Java expresa mejor fecha, hora y desplazamiento.

Relaciones diferidas

Las asociaciones se declaran principalmente con FetchType.LAZY. Así no se carga todo el grafo de la clínica cada vez que se consulta una fila. Los DAO que necesitan mostrar relaciones pueden usar consultas con JOIN FETCH.

La aplicación no altera el esquema

jakarta.persistence.schema-generation.database.action=none protege la estructura existente. La base de datos ya está creada y el proyecto se limita a operar sobre ella.

Pregunta: ¿Por qué las entidades y los DAO implementan Serializable?
Los modelos con alcance de vista pueden conservarse entre solicitudes y el contenedor puede necesitar serializar su estado. Mantener serializables los objetos participantes evita problemas en ese ciclo de vida y sigue la observación realizada al proyecto.

12. Plantilla e internacionalización

Las páginas usan /WEB-INF/plantillas/general.xhtml. La ubicación bajo WEB-INF impide abrir la plantilla directamente y obliga a consumirla mediante Facelets.

La plantilla concentra:

  • Título y encabezado.
  • Menú PrimeFaces agrupado por áreas.
  • Zona de mensajes.
  • Selector de idioma.
  • Contenido y pie de página.

faces-config.xml registra el bundle con la variable msg. Existen recursos para español, inglés y francés. Las páginas usan claves como #{msg['boton.guardar']} en lugar de repetir texto fijo.

Pregunta: ¿Qué ventaja da la plantilla?
Evita copiar navegación, selector de idioma y mensajes en cada página. Un cambio común se realiza una vez y se refleja en todas las vistas.

13. Configuración de PrimeFaces y Liberty

PrimeFaces está declarado en Maven con clasificador jakarta y alcance provided. Eso significa que el código compila contra PrimeFaces, pero el WAR no necesita empaquetar otra copia porque Liberty lo proporciona como biblioteca global.

<dependency>
    <groupId>org.primefaces</groupId>
    <artifactId>primefaces</artifactId>
    <version>15.0.17</version>
    <classifier>jakarta</classifier>
    <scope>provided</scope>
</dependency>

El archivo primefaces-lib.xml define la biblioteca global y busca primefaces-15.0.17-jakarta.jar dentro de ${wlp.install.dir}/lib. Se cambió el nombre genérico openliberty.xml por uno que explica su propósito.

Conexión a la base

persistence.xml usa la unidad clinica_ppi y solicita el datasource JTA jdbc/GalenoSV. La definición del datasource pertenece al servidor Liberty externo; no está duplicada dentro de la aplicación.

Limitación de portabilidad conocida:
En esta computadora funciona porque Liberty ya tiene configurado jdbc/GalenoSV. Otra persona que clone el repositorio necesitará configurar el mismo datasource, el controlador PostgreSQL y la biblioteca global de PrimeFaces en su servidor.

  5. Mostrar Persona: explicar que los campos corresponden a su entidad y no al formulario genérico inicial.

17. Preguntas probables y respuestas

¿Por qué usar DAO si JPA ya tiene EntityManager?
Porque el DAO concentra las operaciones de persistencia y evita que la interfaz dependa directamente de JPA. También ofrece un lugar único para consultas específicas y manejo coherente de errores.
¿Por qué no colocar todo en el modelo JSF?
Porque mezclaría estado visual, navegación y persistencia. Separarlo facilita probar los DAO y cambiar la interfaz sin reescribir el acceso a datos.
¿Qué diferencia hay entre Examen y TipoExamen?
TipoExamen clasifica; Examen representa el estudio concreto. “Radiológico” es tipo y “Radiografía panorámica” es examen.
¿Por qué existe una entidad intermedia?
Porque la relación tiene identidad y datos propios, como fecha y observaciones. Además permite que la asociación evolucione sin cargar esos datos en ninguna de las dos entidades principales.
¿Por qué usar un modelo @Dependent?
Porque el modelo de la relación es un detalle del examen seleccionado y debe acompañar el ciclo de vida del modelo principal.
¿Por qué @ViewScoped y no @RequestScoped?
Una pantalla JSF realiza varias solicitudes AJAX. El alcance de vista conserva selección y estado CRUD durante esas solicitudes.
¿Por qué usar LazyDataModel?
Para pedir únicamente el rango visible de filas y el total, en lugar de cargar toda la tabla en memoria.
¿Por qué PrimeFaces tiene alcance provided?
Porque la biblioteca se entrega desde Liberty como biblioteca global. Empaquetarla también en el WAR duplicaría clases y podría provocar conflictos de versión.
¿Por qué no generar automáticamente la base con JPA?
Porque el esquema ya existe y es la fuente de verdad. La acción none evita modificaciones accidentales durante el despliegue.
¿Por qué OffsetDateTime?
Es la API moderna para fecha y hora con desplazamiento; reemplaza el uso heredado de Date y @Temporal.
¿La aplicación ya está lista para producción?
Está lista para el alcance académico actual, no para producción. Antes harían falta seguridad, auditoría, más pruebas, configuración portable y cambiar el modo Development.
¿Por qué NetBeans muestra tres paquetes?
Java considera boundary, boundary.jsf y boundary.conversores paquetes distintos. La vista plana los muestra como hermanos, aunque físicamente los subdirectorios estén dentro de boundary.
¿Se abandonó el patrón del proyecto base?
No. Se mantuvieron entidad, DAO, modelo JSF, plantilla y página. Las diferencias responden al dominio odontológico y a relaciones que el ejemplo original no necesitaba resolver completamente.

19. Resumen final para memorizar

Arquitectura: XHTML → Model → DAO → Entity → PostgreSQL.

Reutilización: AbstractModel<T> y DefaultDAO<T> reúnen el CRUD común.
